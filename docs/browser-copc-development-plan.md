# 纯浏览器端大文件点云系统开发方案

## 目标

本文档给出一个完整的开发方案，用于在**无服务端**前提下，基于**浏览器 + Web Workers + 本地缓存 + COPC 思路**实现大文件点云系统。

目标能力包括：

- 在浏览器中打开超大点云文件
- 支持本地文件方式使用，无需服务端
- 支持渐进式预览与局部高精度细节展示
- 支持交互式选择、过滤、删除、保留
- 支持本地导出
- 支持后续持续演进

这里的“完整细节展示”指的是：

- 整个数据集都可访问
- 当前视图区域可逐步加载到最高可用精度
- 不是将全部点一次性常驻浏览器内存

---

## 1. 设计原则

整个系统必须遵循以下原则：

### 1.1 不再使用全量点数组模型

不能再采用“打开文件后把所有显示点解析为一份大 `Float32Array/Uint8Array`”的模式。

原因：

- 超大文件会直接触发浏览器内存压力
- 颜色切换、选择、高亮、编辑都会重复复制大数组
- 无法支撑真正的大文件交互

### 1.2 浏览器只维护当前所需数据

浏览器只保存：

- 当前相机附近或视锥内需要的节点
- 当前显示分辨率所需的点块
- 当前会话的编辑日志
- 本地缓存索引和小块数据

浏览器不保存：

- 整个文件的全量点对象
- 全量编辑后的点云副本
- 全量 undo 快照

### 1.3 计算必须从主线程移出

主线程只负责：

- UI
- 相机控制
- 调度
- 渲染提交

重任务必须放到 Worker：

- 文件解析
- 节点解码
- 采样
- 筛选
- 选择计算
- 导出重写

### 1.4 浏览格式优先使用层级化结构

浏览器端适合的不是原始顺序 LAS 流，而是带空间索引和层级的结构。

优先顺序建议：

1. 直接支持 `COPC`
2. 对普通 `LAS/LAZ` 在本地转换为可缓存的分块索引格式

---

## 2. 系统目标范围

### 2.1 支持的输入

- `.copc.laz`
- `.las`
- `.laz`

推荐策略：

- `COPC` 直接浏览
- `LAS/LAZ` 首次打开时本地索引化，再进入浏览

### 2.2 支持的核心能力

- 打开本地点云文件
- 显示整体概览
- 缩放到局部查看细节
- 切换颜色模式
- 局部框选和过滤
- 删除与保留操作
- Undo / Redo
- 本地导出新文件

### 2.3 不建议在第一阶段承诺的能力

- 同时打开多个超大数据集并联动编辑
- 浏览器内完成重型网格重建
- 任意复杂几何布尔运算
- 即时全量重新分类

这些可以后续扩展，但不应放入第一阶段核心目标。

---

## 3. 总体架构

推荐系统分为 6 层：

1. 文件接入层
2. 元数据与索引层
3. Worker 计算层
4. 本地缓存层
5. 客户端调度层
6. 渲染与交互层

可概括为：

```text
本地文件 / 文件句柄
        |
        v
文件接入层
        |
        v
元数据解析 / COPC 索引读取 / LAS-LAZ 本地索引化
        |
        v
Worker 计算层 <----> 本地缓存层(OPFS / IndexedDB)
        |
        v
客户端节点调度器
        |
        v
渲染层(WebGL/WebGPU)
        |
        v
交互与编辑日志
        |
        v
导出 Worker
```

---

## 4. 文件接入层设计

### 4.1 推荐接入方式

优先使用：

- `File System Access API`

备选方式：

- 拖拽文件
- `input[type=file]`

推荐 `File System Access API` 的原因：

- 更适合超大文件
- 可以重复读取，不需要反复选择
- 导出时可直接写入目标文件
- 更容易做长期会话和本地缓存绑定

### 4.2 文件类型判定

接入后第一步应做文件识别：

- 判断是否为 `COPC`
- 判断是否为 `LAS`
- 判断是否为 `LAZ`
- 读取头信息和点格式

输出统一的 `DatasetDescriptor`，至少包含：

- 文件类型
- 文件大小
- 点格式
- 总点数
- 坐标范围
- 可用属性
- 坐标系信息

---

## 5. 元数据与索引层设计

### 5.1 对 COPC 的处理

若输入为 `COPC`：

- 直接读取层级结构
- 提取根节点和包围盒
- 获取节点偏移、点数、LOD 信息

这时不需要再生成新的全局浏览索引。

### 5.2 对 LAS/LAZ 的处理

若输入为普通 `LAS/LAZ`：

- 首次打开先做本地索引化
- 生成内部浏览索引
- 可选择把结果持久化到 OPFS

本地索引化应完成：

- 空间分块
- 构建层级结构
- 生成低 LOD 概览
- 建立节点元数据表
- 建立属性统计表

### 5.3 统一元数据结构

无论源格式如何，前端浏览层都应只面对统一的数据集元数据结构，例如：

- `datasetId`
- `bounds`
- `pointCount`
- `attributes`
- `rootNodeId`
- `hierarchyDepth`
- `sourceFormat`
- `cacheVersion`

这样可以让渲染层和调度层不关心底层来源是 COPC 还是原始 LAS。

---

## 6. Worker 计算层设计

这是整个系统最关键的部分。

至少需要以下 Worker：

### 6.1 Metadata Worker

职责：

- 读取文件头
- 识别 LAS / LAZ / COPC
- 解析元数据
- 生成 `DatasetDescriptor`

输入：

- 文件句柄或 Blob 片段

输出：

- 元数据对象

### 6.2 Indexing Worker

仅用于普通 `LAS/LAZ` 的首次本地索引化。

职责：

- 顺序扫描原始文件
- 构建空间节点
- 生成本地 LOD
- 输出节点块和元数据到 OPFS

输入：

- 文件句柄
- 索引配置

输出：

- 本地浏览索引

### 6.3 Tile Decode Worker

职责：

- 按节点 ID 读取数据块
- 解码位置、颜色、强度、分类等属性
- 返回可直接用于渲染的数据块

输入：

- 数据集标识
- 节点 ID
- 需要的属性列表

输出：

- `TileData`

### 6.4 Selection Worker

职责：

- 根据当前视锥或屏幕矩形做 tile 级筛选
- 对候选 tile 进行局部精筛
- 返回命中点或命中规则

输入：

- 相机矩阵
- 屏幕框
- 候选 tile

输出：

- 选中结果

### 6.5 Export Worker

职责：

- 扫描原始文件或本地索引
- 应用编辑日志
- 生成输出文件
- 分块写入 OPFS 或目标文件句柄

输入：

- 原始文件句柄
- 编辑日志
- 导出格式

输出：

- 导出结果文件

### 6.6 Worker 通信原则

建议统一采用消息协议，消息包含：

- `requestId`
- `type`
- `payload`
- `transferables`

大数组应尽量用 `Transferable` 传输，避免结构化克隆复制。

---

## 7. 本地缓存层设计

纯浏览器大文件系统没有本地缓存就不可用。

### 7.1 缓存技术选型

推荐：

- `OPFS` 作为主缓存

可选：

- `IndexedDB` 存元数据和小对象

### 7.2 应缓存的内容

本地缓存建议包含：

- 数据集元数据
- 节点层级信息
- 节点点块
- 低 LOD 快照
- 属性统计
- 编辑日志
- 导出中间文件

### 7.3 缓存结构

建议按数据集隔离，例如：

```text
cache/
  datasets/
    {datasetId}/
      metadata.json
      hierarchy.bin
      tiles/
      edits.json
      exports/
```

### 7.4 缓存淘汰

应支持：

- 数据集级清理
- 节点块级淘汰
- 基于容量上限的清理

否则长期使用会导致本地存储失控。

---

## 8. 客户端调度层设计

客户端调度层负责在“当前视图”和“本地资源预算”之间做平衡。

### 8.1 调度器职责

- 根据相机判断需要哪些节点
- 判断每个节点应加载哪个 LOD
- 控制总点预算
- 控制总内存预算
- 控制解码并发
- 决定哪些节点可卸载

### 8.2 调度依据

建议综合以下因素：

- 节点包围盒是否进入视锥
- 节点到相机距离
- 节点投影后的屏幕覆盖面积
- 节点误差是否超过当前阈值
- 当前 GPU 点预算

### 8.3 点预算策略

必须引入全局点预算。

例如：

- 低配机器：`1M ~ 2M`
- 中配机器：`3M ~ 5M`
- 高配机器：`5M ~ 10M`

系统不能无限增加显示点数，否则仍会崩溃。

### 8.4 渐进加载流程

推荐流程：

1. 先显示全局低 LOD
2. 相机静止后调度更细节点
3. 局部区域达到高精度
4. 超预算时淘汰远处或低优先级节点

这能保证：

- 首屏快
- 交互稳
- 局部细节足够高

---

## 9. 渲染层设计

### 9.1 数据组织方式

渲染层应改为面向节点，而不是面向单个全局数组。

正确模式：

- `visibleTiles[]`
- 每个 tile 持有自己的 attribute buffer
- 渲染层统一调度这些 tile

### 9.2 颜色模式设计

颜色模式必须 shader 化。

不要：

- 切换颜色模式时在 CPU 上重建整份颜色数组

应该：

- 保留原始属性
- 用 shader 根据 mode 进行计算
- 切模式只更新 uniform

可支持的模式：

- RGB
- Intensity
- Height
- Height + Intensity
- Classification
- 白模

### 9.3 高亮与选择显示

高亮不应复制整份颜色数组。

建议：

- 用单独 overlay layer 表示命中点
- 或使用 selection mask
- 或对候选 tile 单独着色

### 9.4 Picking

大文件点云下不应使用全点 CPU `project()`。

推荐方式：

- 先根据视锥筛 tile
- 再做局部 picking
- 或使用 GPU color picking

### 9.5 渲染技术

可选方向：

- WebGL2
- WebGPU

第一阶段建议先用 WebGL2，原因是兼容性更稳。

---

## 10. 编辑系统设计

### 10.1 编辑模型

编辑必须采用“操作日志”模型，而不是“编辑后点数组”模型。

典型操作包括：

- 删除屏幕框选内点
- 保留空间包围盒内点
- 按分类过滤
- 按高度或强度过滤

### 10.2 编辑日志结构

每条日志建议记录：

- 操作类型
- 空间范围
- 相机信息
- 命中的节点或条件
- 时间戳

例如：

- `deleteBySelection`
- `keepByAABB`
- `filterByClassification`

### 10.3 Undo / Redo

只对操作日志做回退：

- `undo` 撤销最后一条操作
- `redo` 恢复撤销操作

不要再存整份点云快照。

### 10.4 实时反馈

为保证交互体验：

- 当前已加载节点应立即应用编辑日志
- 未加载节点在后续加载时自动套用日志

这样可以做到：

- 用户看到即时变化
- 系统仍然不需要维护全量编辑后的点云

---

## 11. 导出系统设计

### 11.1 导出原则

纯浏览器端也可以导出，但必须采用**流式导出**。

不能：

- 把全部输出拼成一个超大 `Blob`

必须：

- 使用 Worker
- 分块读取
- 分块应用编辑日志
- 分块写入 OPFS 或文件句柄

### 11.2 导出支持格式

推荐支持：

- LAS
- LAZ
- COPC

### 11.3 导出流程

1. 用户触发导出
2. Export Worker 读取原始数据或本地索引
3. 重放编辑日志
4. 生成输出头信息
5. 分块写入输出文件
6. 提供下载或另存

### 11.4 导出中的进度反馈

导出必须具备：

- 总进度
- 当前阶段
- 可取消
- 失败恢复提示

否则大文件导出体验会很差。

---

## 12. 针对 COPC 的专项设计

### 12.1 为什么推荐 COPC

在无服务端场景下，`COPC` 仍然很有价值，因为它天然适合：

- 层级化访问
- 随机节点读取
- 渐进式显示
- 大文件场景

### 12.2 COPC 的客户端使用方式

浏览器端对 `COPC` 的使用建议为：

1. 读取 metadata 和 hierarchy
2. 根据当前视图决定需要哪些节点
3. 按节点读取对应字节范围
4. 在 Worker 中完成解码
5. 返回可渲染 tile

### 12.3 非 COPC 文件的处理策略

对于普通 `LAS/LAZ`：

- 首次打开时做本地索引化
- 后续浏览尽量走本地层级索引

也就是说：

- `COPC` 是原生浏览格式
- `LAS/LAZ` 是源文件格式

## 13. 性能与资源预算

### 13.1 内存预算

系统必须设定浏览器内存预算，不能无限制增长。

建议控制：

- 当前活动 tile 数量
- 当前 GPU 点预算
- 当前 CPU 侧缓存大小

### 13.2 GPU 预算

应提供动态质量设置：

- 低配模式
- 平衡模式
- 高质量模式

不同模式下调整：

- 点预算
- 节点精度阈值
- 缓存深度

### 13.3 Worker 并发

并发数量不宜过高。

建议：

- 解码 Worker：`2 ~ 4`
- 选择 Worker：`1 ~ 2`
- 导出 Worker：`1`

避免并发过高导致 CPU 抢占和页面抖动。

## 15. 开发阶段建议

### 15.1 第一阶段：可浏览

目标：

- 本地打开 `COPC`
- 元数据读取
- 节点调度
- 渐进式显示
- 基础颜色模式

验收标准：

- 能稳定浏览大文件
- 缩放到局部可看到更高细节
- 主线程不卡死

### 15.2 第二阶段：兼容 LAS/LAZ

目标：

- 解析 `LAS/LAZ`
- 本地索引化
- 建立 OPFS 缓存
- 与 `COPC` 统一浏览

验收标准：

- 普通 LAS 首次打开后可进入同一套浏览流程

### 15.3 第三阶段：选择与编辑

目标：

- tile 级选择
- 局部高亮
- 编辑日志
- Undo / Redo

验收标准：

- 大文件下框选和删除仍然可交互

### 15.4 第四阶段：本地导出

目标：

- 流式导出
- 支持 LAS / LAZ / COPC
- 进度可见

验收标准：

- 不通过超大 Blob 也能完成导出

## 16. 对当前项目的改造建议

当前 `web` 目录代码的主要问题是：

- 仍在用全量 `PointData`
- 颜色模式是 CPU 全量重算
- 选择是全点投影
- 编辑是数组复制
- 保存是全量组 Blob

因此不建议继续在当前结构上做局部补丁式优化。

更合理的改造顺序是：

1. 先把 `loadLAS(file, maxPoints)` 改为“数据集接入 + 节点流”
2. `Viewer` 改为接收 `visibleTiles[]`
3. 颜色模式改 shader 化
4. 选择逻辑改为 Worker + tile 筛选
5. 编辑改为日志模型
6. 导出改为 Worker 流式输出

---

## 17. 风险与注意点

### 17.1 浏览器兼容性

不同浏览器对以下能力支持不一致：

- File System Access API
- OPFS
- 大文件稳定性
- WebGL / WebGPU 行为

建议优先以 Chromium 系浏览器作为目标平台。

### 17.2 LAZ 支持

如果要支持 `LAZ`：

- 必须明确采用何种浏览器端解压方案
- 不能只在 UI 上接受 `.laz`，却没有真实解码实现

### 17.3 大文件首开耗时

普通 `LAS/LAZ` 首次打开时，本地索引化本身可能是耗时操作。

必须在交互上提供：

- 明确进度
- 处理中状态
- 可取消
- 失败恢复

### 17.4 本地缓存空间

超大文件缓存会快速占用磁盘空间。

必须提供：

- 缓存管理
- 清理入口
- 数据集级删除

---

## 18. 结论

在无服务端前提下，基于**浏览器 + Web Workers + OPFS + COPC/本地层级索引**，可以构建一个可用的大文件点云客户端。

这套方案的关键不在于“优化读取速度”，而在于彻底改变数据模型：

- 从“全量点数组”改为“节点化、层级化数据集”
- 从“主线程重计算”改为“Worker 并行处理”
- 从“全量编辑副本”改为“操作日志”
- 从“整文件 Blob 导出”改为“流式导出”

如果按本文档的架构执行，就有可能在纯浏览器端稳定支持超大点云文件的预览、细节查看、编辑和导出。
